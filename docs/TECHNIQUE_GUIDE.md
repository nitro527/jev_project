# 문제 유형별 기법 선택 가이드

> 집 PC Qwen3.5-4B 실험에서 본 **경향**을 기준으로 정리했다. 정확한 수치는 사내 Qwen3.8로 다시 측정해야 한다
> (`bench/improve_eval.py`, `docs/IMPROVE_AND_BENCHMARK.md`). 개념 설명은 `docs/CONCEPTS.md`.

## 전제: logprobs가 있어야 한다
이 가이드의 기법 중 **보정(devcal, bc)과 cascade / confidence gate는 모두 확률이 있어야** 동작한다.
확률은 서버가 `logprobs`를 돌려줘야만 얻을 수 있다(`probe_endpoint.py` 2번 항목).
- logprobs가 없으면 1토큰 답(빠른 분류)만 가능하다. 도메인 판단에서 예시 + 보정(0.925)을 쓸 수 없고 예시만(0.537) 남는다.
- **"확률을 0~100으로 답해"로 대신하지 않는다.** 실험에서 거의 0/100만 나왔고 오답에도 100%를 붙였다.

## 용어 (쉽게)
| 이름 | 한 줄 설명 |
|---|---|
| **raw** | 그냥 물어보고 첫 글자(A/B…)의 확률을 읽는다. 기본 Jev 방식이고 0.1초 걸린다 |
| **plain** | 모델이 JSON으로 답을 직접 쓴다. 평소 LLM을 쓰는 방식이다 |
| **few-shot** | 물어보기 전에 정답이 붙은 예시를 보여준다 |
| **보정 (devcal)** | 정답을 아는 20~50건으로 모델의 치우침(예: "예"라고 말하는 버릇)을 재서, 이후 확률을 고쳐 읽는다 |
| **보정 (bc)** | 한 번에 판정한 묶음의 평균으로 치우침을 추정해 고친다. 정답이 필요 없다 |
| **thinking** | 답하기 전에 속으로 풀이를 쓰게 한다. 정확해지지만 300배 이상 느리다 |
| **cascade** | 확신도가 낮은 건만 다음 단계(thinking, Claude, 사람)로 넘긴다. 보정이 아니라 **넘기는 구조**다 |
| **think-then-decide** | thinking으로 풀이를 쓰게 한 뒤, 풀이 끝 자리에서 A/B 확률을 읽는다. 이 프로젝트 cascade의 2단계 |
| **말로 한 확률** | "확률을 숫자로 답해"라고 시켜서 받은 숫자. 자기 보고라서 믿을 수 없다(쓰지 않는다) |

## 비용 감각 (항목당, 집 PC 가짜 서버 기준)
| 방식 | 출력 토큰 | 시간 | 비고 |
|---|---|---|---|
| raw / bc / devcal | 1 | 약 0.1초 | 보정은 계산만 하므로 무료 |
| few-shot (+보정) | 1 | 0.1~0.3초 | 입력만 2.5~6배 늘고 시간은 거의 그대로 |
| perm | 선택지 수 | 선택지 수만큼 배로 | 비용 대비 효과 없음 |
| plain | 15~30 | 약 1~1.5초 | 8~18배 느림 |
| thinking (cascade, plain+thinking) | 수백~수천 | 30초~3분 이상 | 1000배 이상 느림. 예산이 모자라면 답이 아예 안 나온다 |

**시간을 잡아먹는 건 출력 토큰이다**(입력은 병렬 처리, 출력은 한 토큰씩 순서대로 생성). 그래서 Jev 방식에서는
입력을 늘리는 개선(예시 넣기)은 싸고, 출력을 늘리는 방식(생성, thinking)은 비싸다.
스트리밍으로 나눠 보면 plain(출력 20토큰)의 전체 시간 중 **출력 생성이 67~92%**, thinking은 99.7% 이상이다.
인프라가 좋아지면 절대 시간은 줄지만 이 비중은 거의 그대로다. 사내 수치는 `bench/latency_profile.py`로 잰다.

## 먼저 볼 것: 양이 많은가?
- **판단할 양이 적고(수십 건) 정확도가 최우선**이면 → Jev를 쓰지 말고 Claude나 thinking을 그대로 쓴다.
- **양이 많거나(수천 건 이상) 빨라야 하면** → 아래 표대로 Jev를 쓴다.

## 문제 유형 → 기법

| # | 문제 유형 | 예 | 쓸 기법 | 경향 (4B) |
|---|---|---|---|---|
| 1 | **일반 분류, 라우팅** (상식으로 풀리는 것) | 문의 담당팀, 뉴스 주제, 감성, 스팸 | **raw**. 묶음으로 판정할 때는 **bc**를 켠다(비용 0) | raw가 이미 85~88%이고, 다른 기법은 차이가 거의 없다 |
| 2 | **도메인 규칙 판단** (조직이나 장비의 기준을 알아야 하는 것) | 로그 줄이 장애인가, 이 이벤트가 리뷰 대상인가 | **few-shot 예시 + 정답 20~50건으로 보정(devcal)**. 정답이 없으면 few-shot + bc | **67% → 92%**. 가장 큰 효과를 봤다. thinking은 거의 도움이 되지 않았다(+2%p) |
| 3 | **계산, 날짜, 개수, 수치 비교** | 한도 초과 여부, 100일 뒤 요일, 재시도 횟수 | ① **코드로 계산해서 결과를 state에 넣는다**(1순위) ② 불가피하면 thinking을 **끝까지** 하게 한다 | raw 7/10, thinking을 끝까지 하면 10/10. 중간에 끊으면 효과가 없다 |
| 4 | **함정이 있거나 여러 조건이 얽힌 판단** | 인보이스 중복 + 계좌 변경 사기, 여러 조건 조합 | **질문을 잘게 쪼개고**(조건 하나에 질문 하나) **조합은 코드로**. 애매한 건 cascade로 넘긴다 | Jev 78%, plain 86%. 확신도 0.8 이상만 채택하면 92%(절반 이상이 여기서 끝난다) |
| 5 | **추출** (어디가 문제인가) | 근본 원인 로그 줄, 해당 필드 | **후보를 코드로 추려서 choice 선택지로** 준다 | 첫 증상 줄은 정확히 골랐다(0.88). 애매한 원인 줄은 낮은 확신도로 표시했다(0.51) |
| 6 | **순위, 관련도** | 검색 결과 재정렬, 유사 사례 찾기 | 항목마다 noul "관련 있나?"를 묻고 **P(yes)로 정렬**한다 | 관련 문서 0.95, 무관한 문서 0.00으로 순서가 자연스러웠다 |
| 7 | **선택지가 많은 분류** (26개 초과) | 세부 장애 코드, 세부 문의 유형 | **계층 분류**: 대분류를 고른 뒤 세부를 고른다 | 2단계 모두 1.00, 174ms |
| 8 | **열린 질문, 설명, 요약** | "원인이 뭐야?", "요약해줘" | Jev로는 불가능하다 → `llm_chat`이나 Claude | – |

## 공통 규칙
1. **확신도로 넘길 건을 고르려면(cascade) 먼저 보정한다.** 보정하지 않은 raw는 도메인 문제에서 **틀린 답에 더 확신**했다.
   그러면 넘겨야 할 오답이 통과한다.
2. **선택지 설명에 판단 기준을 적는다.** 예: "BLER 10% 미만이고 재시도 후 성공하면 normal".
   **"해당 없음" 선택지**(other, normal)를 반드시 넣는다.
3. **쓰지 않는 기법**: 선택지 순서를 섞어 여러 번 묻기(perm, 비용만 증가)와 빈 입력으로 치우침 재기(cc, 불안정).
4. **예시(few-shot)는 도메인 문제에만** 쓴다. 일반 분류나 긴 지문에 넣으면 오히려 떨어졌다.
5. **dev가 작으면 보정이 과적합**할 수 있다. 가능하면 50건 이상의 정답을 쓴다.
6. **thinking을 쓸 때는 끝까지 생각할 예산을 주고, 예산 초과를 처리한다.** 중간에 끊긴 풀이는 거의 도움이 되지 않았고,
   plain+thinking은 예산(4096)을 넘겨 답이 없는 경우가 절반이었다.
7. **긴 로그를 통째로 넣지 않는다.** 입력 3,000토큰이면 판단 1회에 0.9~1.6초다(가짜 서버 기준). 필요한 줄만 코드로 추려서 넣는다.

## cascade의 2단계로 무엇을 붙이나
| 2단계 | 언제 | 비용 |
|---|---|---|
| think-then-decide (같은 Qwen, thinking) | 계산·추론이 필요한 애매한 건 | 건당 수십 초 |
| plain (생각 없이 JSON 생성) | 형식이 다른 답이 필요할 때. 확률은 없다 | 건당 약 1초 |
| Claude | 설명이나 종합 판단이 필요한 건 | 외부 호출 |
| 사람 (엔지니어 리뷰) | 영향이 큰 결정 | – |

## 흐름으로 보면
```
판단할 양이 적다 ──────────────────────────▶ Claude / thinking 그대로
      │ 많다
      ▼
계산·날짜·수치가 필요하다 ─▶ 코드로 계산해서 state에 넣기
      ▼
도메인 규칙이 필요하다 ─▶ few-shot + 보정 (정답 20~50건)     일반 상식이면 raw (+bc)
      ▼
Jev 판정 → 보정된 확신도 높음 ─▶ 자동 채택
                 └ 낮음 ─▶ cascade: thinking(끝까지) → 그래도 애매하면 Claude / 사람
```

## 모뎀 로그에 대입하면
| 하고 싶은 것 | 유형 | 방법 |
|---|---|---|
| 로그 윈도의 장애 유형 분류 | 2 | 유형별 예시 로그 + 엔지니어 정답 20~50건으로 보정 |
| BLER이나 재시도 횟수로 이상 판단 | 3 | 수치는 코드로 계산해 state에 넣고, Jev는 의미만 판단 |
| 원인 줄 찾기 | 5 | 에러와 경고 줄을 코드로 추려서 선택지로 준다 |
| 리뷰가 필요한 윈도 고르기 | 2 + cascade | 보정된 needs_review 확신도로 자동 처리 / 리뷰 / 무시를 나눈다 |
| 세부 원인 코드 (수십 종) | 7 | 대분류(RACH, HARQ, RLF…) → 세부 |
| "왜 끊겼는지 설명해줘" | 8 | Claude가 한다. Jev는 대상 윈도를 추려주는 역할 |
