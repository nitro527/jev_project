## 1. 한눈에 보기

**Jev 방식(우리 구현) = 모델에게 질문을 한 번 통과시키고, 다음에 올 글자가 A일지 B일지의 확률표를 직접 읽는 것.**
텍스트를 생성하지 않고, 추가 학습도 없다. 모델은 평범한 Qwen 그대로다.

```
질문:  "이 로그 줄이 장애인가?  A. Yes  B. No   글자만 답해"
            │ 모델을 한 번 통과 (출력 1토큰, logprobs 켬)
            ▼
다음 글자 확률표:  A 0.97 · B 0.02 · (기타 0.01)
            │ A와 B만 비교
            ▼
답: "예", 확률 0.97
```

이 방식의 가치는 두 가지다.
1. **빠르고 싸다**: 출력이 항상 1토큰이다.
2. **확률이 나온다**: 확률로 애매한 건을 골라내고(confidence gate), 치우침을 보정할 수 있다.

## 2. raw와 plain은 실제로 무엇이 다른가

같은 모델, 같은 가중치, 같은 계산 방식이다. thinking도 둘 다 끈다. 차이는 **세 군데**다.

### ① 질문을 쓰는 방식 (프롬프트)
같은 BGL 로그 한 줄에 대해 실제로 보낸 프롬프트다.

**raw** (`jev_api.build_user_content`)
```
State:
RAS KERNEL FATAL data TLB error interrupt

Question: This is one line from a supercomputer (Blue Gene/L) system log. Does this line report an actual
failure or alert that operators should act on, rather than routine or self-corrected informational activity?
A. Yes
B. No

Answer with the option letter only.
```

**plain** (`jev_api.build_plain_prompt`)
```
State:
RAS KERNEL FATAL data TLB error interrupt

Answer every question below.
- "answer": This is one line from ... informational activity? Answer "yes" or "no".

Reply with ONLY a JSON object, no other text, in this form: {"<question key>": {"answer": <answer>, "confidence": <0-100>}, ...}
```

### ② 요청 설정
| | raw | plain |
|---|---|---|
| `max_tokens` | **1** (한 글자 만들고 멈춤) | 512 (다 쓸 때까지) |
| `logprobs` / `top_logprobs` | **켬 / 20** (다음 글자 후보 상위 20개의 확률) | 끔 |

### ③ 답을 꺼내는 방식 (가장 큰 차이)
- **raw**: 모델이 "고른" 글자를 보는 게 아니라 **확률표를 우리가 읽는다.**
  `A: 0.97, B: 0.02 → A와 B만 다시 정규화 → "예" 0.98`
- **plain**: 모델이 **다 쓴 글을 파싱**한다.
  `{"answer": {"answer": "yes", "confidence": 100}} → "yes", 확신도 100 (모델이 스스로 적은 숫자)`

### 그러면 추론 방식이 다른가? → 아니다
- 둘 다 같은 모델이 같은 방식으로 계산한다. raw는 "결과를 고정"하는 게 아니라, **출력을 한 글자에서 멈추고 그 순간
  모델이 A와 B 중 어디로 얼마나 기울어 있는지를 들여다보는 것**이다.
- plain도 `{"answer": {"answer": "` 같은 **형식 글자**를 몇 개 쓴 다음 "yes"를 쓴다. 그 순간의 판단은 raw와 본질적으로 같다.
  앞의 글자들은 풀이가 아니라 형식이기 때문이다(6장).
- **주의(엄밀성)**: 두 방식은 프롬프트도 조금 다르다(A/B 글자 vs yes/no 단어, JSON 요구, plain은 질문을 한 프롬프트에 묶음).
  그래서 둘의 정확도 차이가 "확률을 읽느냐, 쓴 글을 받느냐" 때문인지 "프롬프트 차이" 때문인지 **완전히 분리되지는 않는다.**
  엄밀히 비교하려면 같은 프롬프트로 한쪽은 확률을 읽고 다른 쪽은 생성하게 해야 한다(HANDOFF 6장 TODO).

## 3. 두 개의 부품: "출력 1토큰"과 "logprobs"

흔히 "Jev = 출력을 1토큰으로 강제한 것"이라고 요약하지만, 실제로는 **서로 다른 역할을 하는 두 부품**이다.

| 부품 | 역할 | 없으면 |
|---|---|---|
| **출력 1토큰** (`max_tokens=1`) | **속도와 비용** | 느려지고 비싸진다. 기능은 돌아간다 |
| **logprobs** (다음 글자 확률표) | **확률** (얼마나 확신하는가) | **답은 나오지만 확률이 사라진다** |

- logprobs 없이 `max_tokens=1`로 보내도 모델은 "A"를 출력한다. **빠르고 싸게 답은 받을 수 있다.**
  하지만 그게 0.51로 겨우 A인지, 0.99로 확실한 A인지는 알 수 없다.
- 확률이 없으면 이번 실험에서 찾은 개선이 **대부분 불가능**해진다.
  - 보정(devcal, bc): 기준선을 옮기려면 확률이 있어야 한다 → 불가능
  - confidence gate / cascade: 애매한 건을 고르려면 확률이 있어야 한다 → 불가능
  - 결과적으로 BGL 로그 판정이 **0.925(예시 + 보정) → 0.537(예시만, 답만 받는 경우와 같다)**로 떨어진다.
- 그래서 **이 방식이 제대로 동작하려면 logprobs가 사실상 필수**다. logprobs가 없으면 "그냥 빠른 분류기"가 된다.
  사내에서 `probe_endpoint.py`의 2번 항목(logprobs가 게이트웨이를 통과하는가)을 가장 먼저 확인하는 이유다.

## 4. "확률로 답해"라고 시키면 안 되나? (logprobs vs 말로 한 확률)

모델에게 "Yes일 확률을 0~100 숫자로만 답해"라고 시키는 방식을 **verbalized confidence(말로 한 확신도)**라고 한다.
같은 문제로 직접 비교했다(`bench/verbal_vs_logprob.py`). 두 방식의 프롬프트는 마지막 지시문 한 줄만 다르다.

| | logprobs로 읽은 확률 | "0~100으로 답해" (말로 한 확률) |
|---|---|---|
| **BGL 로그** 정확도 | 0.675 | 0.588 |
| 나온 값의 종류 | **39가지** | **2가지 (0이 57번, 100이 23번)** |
| 오답의 확신도 | 오답 26건. 높은 것은 0.94~0.97 | 오답 33건 **전부 100%** |
| 정답 판별력 (AUROC, P(yes) vs 정답) | 0.621 | 0.598 |
| **BoolQ** 정확도 | 0.850 | 0.825 |
| 나온 값의 종류 | 55가지 | 5가지 (100이 60번, 0이 48번) |
| 오답의 확신도 | 오답 18건. 높은 것은 0.90~0.99 | 오답 21건 **전부 100%** |
| 정답 판별력 (AUROC) | **0.902** | 0.836 |
| 출력 토큰 / 시간 | 1 / 약 0.09~0.11초 | 약 5 / 약 0.3초 |
| 파싱 실패 | – | 0 |

### 왜 이렇게 되나
- **logprobs는 측정값**이다. 모델 내부에서 A와 B에 실제로 얼마나 기울어 있는지를 **직접 잰다**(체온계로 체온 재기).
- **말로 한 확률은 자기 보고**다. "몇 %쯤 될 것 같아?"라고 **물어보고 답을 받는** 것이다(환자에게 "열 있는 것 같아요?" 묻기).
  모델은 "확률처럼 보이는 숫자"를 글로 쓸 뿐이고, 그 숫자가 내부 상태를 반영한다는 보장이 없다.
  실제로 거의 0이나 100만 썼고, 틀린 답에도 100을 붙였다. plain의 "confidence 100"도 같은 현상이다.

### 강제할 수는 없나?
- **형식은 강제할 수 있다.** 이번에도 파싱 실패는 0건이었고, vLLM의 guided decoding을 쓰면 숫자만 나오게 완전히 강제할 수도 있다.
- **숫자의 정직성은 강제할 수 없다.** 형식을 강제해도 모델은 여전히 0이나 100을 쓴다.

### 오해하지 말 것: logprobs도 처음부터 정확한 건 아니다
BGL에서 logprob 방식도 오답에 0.94~0.97을 준 경우가 있었다(raw의 AUROC가 낮은 이유). 차이는 이것이다.
- logprobs는 값이 **넓게 퍼져 있어서(39가지)** 보정으로 기준선과 기울기를 고칠 수 있다(7장). 실제로 예시 + 보정으로 0.925가 됐다.
- 말로 한 확률은 **0과 100 두 값뿐**이라 고칠 재료 자체가 없다.

### 결론
| 필요한 것 | logprobs 없이 가능한가 |
|---|---|
| **답만** (예/아니오, 분류) | ✓ plain이나 guided decoding으로 받으면 된다 |
| **믿을 만한 확률** (애매한 건 골라내기, 보정) | 사실상 ✗. 대안은 같은 질문을 N번 샘플링해서 투표 비율을 쓰는 것뿐인데, 비용이 N배라 이 방식을 쓰는 의미가 없어진다 |

## 5. 시간은 어디서 드나: 입력(prefill)과 출력(decode)

LLM은 두 단계로 일한다.
- **입력 처리(prefill)**: 프롬프트 전체를 **한 번에 병렬로** 읽는다.
- **출력 생성(decode)**: 답을 **한 토큰씩 순서대로** 만든다. 토큰 하나마다 모델을 한 번씩 더 통과시킨다.

직접 분리해서 쟀다(`bench/latency_profile.py`).

**[A] 입력은 고정(56토큰), 출력 토큰 수만 변경**
| 출력 토큰 | 1 | 5 | 10 | 20 | 40 |
|---|---|---|---|---|---|
| 시간 | 100ms | 303ms | 533ms | 1,257ms | 2,056ms |

→ 출력이 **1토큰 늘 때마다 약 50ms**

**[B] 출력은 1토큰 고정, 입력 길이만 변경**
| 입력 토큰 | 54 | 324 | 1,524 | 3,024 |
|---|---|---|---|---|
| 시간 | 84ms | 154ms | 661ms | 1,588ms |

→ 입력이 **1토큰 늘 때마다 약 0.5ms**. **출력 1토큰 ≈ 입력 100토큰**의 비용이다.
(문서 정리 때 다시 쟀을 때는 출력 46ms, 입력 0.28ms로 약 160토큰이었다. 측정마다 흔들리므로 **100~160배**로 본다.)

이 공식으로 벤치마크 결과가 설명된다.
- BGL plain: 출력 17토큰 → 100ms + 16 × 50ms ≈ **900ms 예상, 실측 878ms**
- few-shot: 입력이 112 → 284토큰으로 2.5배 늘었지만 시간은 107 → 121ms(1.1배)

그래서 Jev 방식에서는 **입력을 늘리는 개선(예시 넣기)은 싸고, 출력을 늘리는 방식(생성, thinking)은 비싸다.**

주의:
- 입력도 공짜는 아니다. **3,000토큰이면 0.9~1.6초**다. 긴 로그 윈도를 통째로 넣으면 입력 비용이 커진다.
- 가짜 서버는 최적화 커널이 없어서 출력이 특히 느리다. 사내 vLLM에서는 둘 다 빨라지지만
  **출력이 입력보다 훨씬 비싸다는 구조는 같다.** 비교할 때는 서버에 덜 민감한 **토큰 수**를 기준으로 본다.
- Jev 방식은 질문마다 state(로그)를 다시 보낸다. 서버에 **prefix cache**가 켜져 있으면 같은 state의 입력 처리를 재사용해서
  두 번째 질문부터 빨라진다. `latency_profile.py`의 [C]로 사내 서버에서 확인할 수 있다(가짜 서버에는 없다).

## 6. "생각"이란 무엇인가: thinking과 사고 예산

### 모델이 "더 생각하는" 유일한 방법
트랜스포머 모델은 **토큰 하나를 만들 때 하는 계산량이 정해져 있다.** 그래서 모델이 더 많이 계산하는 유일한 방법은
**토큰을 더 만들고, 그걸 다시 읽으면서 다음 토큰을 만드는 것**이다. 연습장에 풀이를 적으며 계산하는 것과 같다.

| | 답 전에 추가로 만드는 토큰 | 실제로 더 생각하나 |
|---|---|---|
| Jev 방식 (raw) | 없음 | ✗ 한 번 통과한 직관 (System 1) |
| plain (thinking 끔) | `{"answer": {"answer": "` 같은 **형식 글자** | **거의 ✗**. 토큰은 더 만들지만 풀이가 아니다 |
| thinking | **풀이 수백~수천 토큰** | **✓** 풀이가 곧 추가 계산이다 (System 2) |

그래서 raw와 plain의 정확도는 대부분 신뢰구간 안에서 비슷했고, **thinking만 계산 문제를 해결했다.**

### 사고 예산 실험 (`bench/think_budget.py`)
여러 단계 계산이 필요한 사실 판단 10문항(37×43=1591 맞나?, 100일 뒤 요일, strawberry의 r 개수, 방망이·공 문제 등).
thinking으로 풀이를 쓰게 하고, **풀이 끝 자리에서 A/B 확률을 읽는다**(think-then-decide).

| 조건 | 정확도 | 평균 확신도 | 평균 생각 토큰 | 평균 시간 |
|---|---|---|---|---|
| thinking 끔 | 7/10 | 0.75 | 0 | 0.1초 |
| 256토큰까지 (대부분 풀이 도중 잘림) | 8/10 | 0.81 | 251 | 12.6초 |
| 1024토큰까지 | **10/10** | 0.98 | 590 | 29.3초 |

- **계산 문제는 풀이를 끝까지 쓰게 하면 다 맞힌다.** 중간에 끊으면 거의 소용없다.
- 대신 **300배 느리다.**
- 풀이를 마친 뒤의 확률은 **0이나 1로 쏠린다**(스스로 확신해버린다). 선행 연구 보고와 같다. **정확도는 오르지만 애매함 신호는 사라진다.**
- **도메인 지식이 없는 문제에는 효과가 작다.** BGL 로그 판정에서 cascade는 +0.025였다. 모델이 모르는 조직의 알림 규칙은
  오래 생각해도 알 수 없다. 모르는 건 예시로 가르쳐야 한다(7장).

### 예산을 넘기면 답이 안 나온다
평소 방식(plain + thinking, 예산 4096토큰)을 태스크당 5건씩 15건 돌렸더니
**8건이 예산 안에 생각을 끝내지 못해 답 자체가 없었다**(답을 낸 7건은 모두 정답). 평균 출력 약 3,300토큰, 건당 약 3분이었다.
→ thinking을 운영에 쓰려면 **예산 초과 처리**(강제로 답 자리를 붙이기, 재시도, 상위 모델로 넘기기)가 반드시 필요하다.

## 7. 보정이란 무엇인가: 예시 + 보정이 왜 통했나

### 비유: 신입 직원에게 로그 판정 맡기기
BGL 로그는 장애인 줄이 모두 FATAL로 찍혀 있지만, **FATAL인데 정상인 줄도 많다**(FATAL 347줄 중 204줄이 정상).

| 방법 | 비유 | BGL 결과 |
|---|---|---|
| **raw** | "이 줄 장애야?"라고만 묻는다. 신입이 FATAL만 보고 장애라고 한다. "예"라고 말하는 버릇도 있다(75%가 예) | 0.675 |
| **few-shot** | 판정 전에 정답이 붙은 예시 4개("이건 장애, 이건 FATAL이지만 정상")를 보여준다. 신입이 **어떤 게 더 장애 같은지 순서는 정확히** 알게 된다(AUROC 0.944). 그런데 긴장해서 거의 다 "예"라고 한다(99%) | 0.537 |
| **보정** | 신입의 "예" 버릇을 알고, 대답을 들은 뒤 **우리가 깎아서 해석**한다. 0.3도 높게 나오는 체온계를 알고 쓰는 것과 같다 | (아래) |
| **few-shot + 보정(devcal)** | 순서 감각(예시) + 기준선 교정(보정) | **0.925** |

### 보정의 세 가지 방법 = 버릇을 어떻게 재느냐의 차이
| 방법 | 버릇을 재는 방법 | 정답 필요 | 결과 |
|---|---|---|---|
| **cc** (contextual calibration) | 빈 종이를 주고 "이거 장애야?"라고 묻는다. 내용이 없는데도 "예"가 많으면 그만큼이 버릇 | ✗ | 불안정. 쓰지 않는다 |
| **bc** (batch calibration) | 오늘 판정한 묶음에서 "예"가 75%였다면, 원래 절반쯤이어야 하니 그 차이가 버릇 | ✗ | few-shot + bc = 0.775 |
| **devcal** | **정답을 아는 20~50건**을 먼저 시켜보고, 얼마나 치우쳤는지 계산해 조정값(temperature, bias)을 정한다 | ✓ (20건) | few-shot + devcal = **0.925** |

### 핵심 교훈
- **순서(판별력)는 예시가, 기준선(치우침)은 보정이 고친다.** 둘 다 필요했다.
- 도메인 지식 없이 확률만 보정하면 소용이 없다(BGL devcal 단독 0.475).
- 일반 상식 문제(BoolQ, AG News)는 raw가 이미 좋아서(0.85~0.88) 차이가 없거나 오히려 나빴다. **예시는 도메인 문제에만** 쓴다.
- **보정은 확률이 있어야 가능하다** → logprobs 필수(3장).

## 8. cascade는 무엇이고 무엇이 아닌가

### cascade는 보정이 아니다
| | 보정 (cc, bc, devcal) | cascade |
|---|---|---|
| 하는 일 | Jev가 낸 **확률 숫자를 고쳐 읽기** | 애매한 건만 **다른 방법으로 다시 판단하기** |
| 판단 과정 | 그대로 (호출 1번, 계산만 조금 더) | 바뀐다 (더 비싼 방법으로 새로 판단) |
| 비유 | 체온계 눈금 맞추기 | 애매하면 정밀검사로 보내기 |
| 비용 | 거의 0 | 넘긴 건마다 수십 초 |

cascade는 **Jev를 개선한 게 아니라 Jev와 다른 방법을 이어 붙인 구조**다. confidence gate와 같은 개념이다.

### 2단계에는 무엇이든 붙일 수 있다
| 2단계 | 설명 | 실측 |
|---|---|---|
| **thinking + Jev 읽기** (이 프로젝트의 cascade) | thinking으로 풀이를 쓰게 하고, 풀이 끝 자리에서 A/B 확률을 읽는다. 파싱 실패가 없고 확률도 나온다 | BGL +0.025, BoolQ +0.008, AG News +0.009 (보정 안 한 raw 위에서) |
| plain (생각 없이 JSON 생성) | 다른 세션의 hybrid. 확신도 0.8 이상은 Jev, 나머지는 plain | 어려운 workflow 72문항: 62/72, plain 단독과 같은 점수를 절반 이상 12배 빠르게 |
| Claude / 사람 | 사내 운영에서 현실적인 최종 단계 | – |

### cascade 전에 반드시 보정한다
cascade는 **1단계의 확신도를 보고 무엇을 넘길지 정한다.** 보정하지 않은 raw는 BGL에서 **틀린 답에 더 확신**했다(AUROC 0.39).
그러면 넘겨야 할 오답이 "확신 있음"으로 통과하고, 맞은 답이 넘어간다. cascade 효과가 작았던 이유 중 하나다.
→ 순서: **few-shot + 보정 → 보정된 확신도가 낮은 것만 cascade → 그래도 애매하면 Claude/사람.**
("보정 후 cascade" 조합은 아직 측정하지 않았다. 다음 실험 후보.)

## 9. plain+thinking이 있는데 Jev는 왜 필요한가

### plain+thinking은 "상한선"이 아니다
평소처럼 LLM을 쓰는 가장 정확한 방식이라서 기준점으로 쓸 수는 있다. 하지만 항상 가장 높지는 않다.
- BGL 로그: **예시 + 보정을 한 Jev(0.925)가 plain(0.75)보다 높았다.** 병목이 "생각 부족"이 아니라 "규칙을 모름"이기 때문이다.
- 게다가 plain+thinking은 **예산 안에 생각을 못 끝내 답이 없는 경우**가 절반이었다(6장).

### Jev의 가치 = 양, 속도, "언제 자신 없는지 아는 것"
로그 1만 윈도를 판정한다면 (GPU 1대, 가짜 서버 기준)
| 방식 | 건당 | 1만 건 |
|---|---|---|
| plain + thinking | 30초~3분 | 약 4~20일 |
| Jev | 0.1초 | **약 17분** |
| Jev → 애매한 20%만 thinking | – | 약 1.5일 |

사내 vLLM에서는 절대 시간이 훨씬 짧겠지만 **출력 토큰 1개 대 수천 개라는 격차는 그대로**다.
Jev는 thinking을 **대체하는 게 아니라, thinking을 어디에 쓸지 골라주는 역할**이다.

### 판단 기준
| 상황 | 추천 |
|---|---|
| 판단할 양이 적다(수십 건), 정확도 최우선 | Claude나 thinking을 그대로 쓴다. Jev가 필요 없다 |
| 양이 많다(로그 윈도 수천~수만, 실시간) | Jev로 전체를 훑고, 애매한 건만 thinking/Claude |
| 도메인 규칙 판단 | 어느 쪽이든 **예시와 보정이 먼저**. 이게 가장 큰 차이를 만들었다 |

## 10. 우리 구현 vs OpenJev vs 진짜 Jev

| | 우리 구현 | OpenJev (TheoLeeCJ) | 진짜 Jev (TypeSafe) |
|---|---|---|---|
| 모델 | 기성 Qwen (사내 Qwen3.8 / 집 Qwen3.5-4B) | Qwen3.5-4B 그대로 (학습·LoRA·전용 헤드 없음) | 전용 모델 (비공개) |
| 답을 얻는 방법 | 한 번 통과, 선택지 글자의 logprob 읽기 | 한 번 통과, 선택지 logit 읽기 ("답 토큰을 샘플링하지 않음") | "토큰을 하나씩 생성하지 않고 모든 확률을 병렬로" (공식) |
| 확률이 정확하도록 | **사후 보정**(devcal, bc)으로 흉내 | 사용자에게 맡김 ("쓸 데이터에서 보정하라") | **RLCD로 모델 자체를 학습**: 정답과 비교해 "70% 확신이면 실제로 70% 맞도록" 보상 (공식) |
| 긴 state를 한 번만 처리 | 질문마다 state를 다시 보냄. 서버 prefix cache에 맡김 | **shared mode**: state의 KV 캐시를 한 번 만들고 질문들로 가지치기. 판단 777개가 38.8초 (새로 계산 시 333초, 약 20배) | 추정: state를 한 번 처리하고 질문을 병렬 가지로 (역추적 추측) |
| 공개 여부 | 이 저장소 | 공개 | **가중치·구조 논문 없음, API만** |

- **우리 구현과 OpenJev의 핵심은 같다**: "출력 1토큰 + 선택지 확률 읽기"가 전부이고 내부에서 특별한 일은 없다.
- **진짜 Jev는 내부를 알 수 없다.** 공식적으로 밝힌 건 병렬 확률 출력과 RLCD 학습뿐이다. 외부 역추적(archerhume)은
  MoE 가능성, 선택지끼리 영향을 주는 구조, 좋은 보정(MMLU 표본 ECE 0.031)을 추측하지만 확인된 것은 아니다.
- **우리의 "예시 + 소량 라벨 보정"은 RLCD의 저렴한 대용품**이다. RLCD는 모델을 학습시켜 확률 자체를 정확하게 만들고,
  우리는 모델을 그대로 두고 나온 확률을 사후에 고쳐 읽는다. 그래서 **우리는 작업마다 보정이 필요하다.**
- OpenJev의 shared mode는 가져올 만하다. 로그 하나에 질문을 여러 개 할 때 효과가 크다.
  사내 vLLM의 prefix caching이 켜져 있으면 비슷한 효과가 이미 날 수 있으니 `latency_profile.py` [C]로 먼저 확인한다.

## 11. 자주 나온 질문 (FAQ)

**Q. thinking을 끄면 단순한 답만 가능한가?**
아니다. 추출(후보 줄 고르기), 재정렬(P(yes)로 정렬), 계층 분류, 여러 기준을 합친 점수 등이 가능하다(`bench/patterns_demo.py`).
다만 **여러 단계 계산**(산술, 날짜, 개수)은 약하다 → 코드로 계산해서 넣거나 thinking cascade를 쓴다.

**Q. Jev는 정해진 형식의 질문에만 답하나?**
질문 문장은 자유지만 **답은 미리 준 선택지 안에서만** 나온다(예/아니오, 선택, 척도). 열린 질문은 `llm_chat`이나 Claude가 한다.
MCP로 쓰면 Claude가 질문과 선택지를 설계해 호출하므로 이 한계가 많이 줄어든다.

**Q. 선택지 고르기는 질문에 선택지를 주는 것인가?**
그렇다. 질문하는 쪽이 `이름: 설명`으로 준다. 모델은 이름보다 **설명**을 보고 판단하므로 판단 기준을 설명에 적고,
**"해당 없음" 선택지**를 반드시 넣는다(없으면 억지로 아무거나 고른다). 최대 26개(A~Z).

**Q. 기법들은 raw를 강화(enhance)한 것인가?**
그렇다. raw를 바꾼 변형들이며 세 종류다: ① 물어볼 때 돕기(few-shot) ② 대답을 고쳐 읽기(보정: cc, bc, devcal)
③ 더 많이/오래 묻기(perm, cascade). 효과는 문제 유형에 따라 다르다(`docs/TECHNIQUE_GUIDE.md`).

**Q. cascade의 두 번째 단계는 plain인가?**
이 프로젝트의 cascade는 **thinking + Jev 읽기**다. 다른 세션의 hybrid는 plain이었다. 2단계는 골라 쓰는 부품이다(8장).

**Q. plain + thinking은 없나?**
있다(`jev_compare`의 `thinking: true`, `improve_eval.py --plain-thinking N`). 느려서 표본만 쟀고, 예산 초과로 절반이 답이 없었다.

**Q. 출력 토큰 수가 중요하다는 건 "출력 이전 동작이 같다"는 전제가 필요하지 않나?**
맞는 지적이고, **우리 구현에서는 그 전제가 성립한다.** 같은 모델에 같은 계산이며, 차이는 모델을 몇 번 통과시키느냐뿐이다.
입력·출력을 분리 측정한 결과가 이를 뒷받침한다(5장). 진짜 Jev는 내부를 모르므로 이 설명은 우리 구현에만 해당한다.

**Q. logprobs가 꼭 필요한가?**
**답만** 필요하면 아니다. **믿을 만한 확률**(보정, 애매한 건 골라내기)이 필요하면 사실상 필수다(3장, 4장).
