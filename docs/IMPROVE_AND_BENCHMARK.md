# 성능 개선 기법 조사 · 실험 · 벤치마크 설계

> 대상 모델: 집 PC 로컬 Qwen3.5-4B (가짜 vLLM 서버 경유, API 경로는 사내와 같음). 작성일 2026-09-19.
> 사내 Qwen3.8에서는 수치가 달라진다. **같은 스크립트로 다시 재는 것이 목적**이다(7장).

## 요약 (결론 먼저)
1. **도메인 판단(실제 로그)에서는 "few-shot 예시 + 소량 라벨 보정"이 압도적으로 효과가 컸다.**
   BGL 실제 로그 장애 판정에서 정확도가 0.675에서 **0.925**로 올랐다. 95% CI는 [0.57,0.78]에서 [0.86,0.97]로, 두 구간이 겹치지 않는다.
   호출 수는 그대로 1회이고, 보정에 쓴 라벨은 dev **20건**뿐이다. 같은 조건에서 일반 생성은 0.75였다.
2. **일반 상식·독해·뉴스 분류에서는 raw가 이미 좋다**(0.85~0.88). 여러 기법의 차이가 신뢰구간 안에 있고,
   few-shot은 오히려 떨어뜨렸다. 이런 작업에는 **raw를 쓰거나, 추가 비용이 없는 batch calibration만 얹는다**.
3. **선택지 순서 섞기(perm)와 contextual calibration(cc)은 이 모델에서 비용 대비 효과가 없었다.**
4. **raw의 확신도는 도메인 판단에서 오답에 더 확신했다**(BGL AUROC 0.39). few-shot과 보정을 적용하면 0.81로 회복된다.
   confidence gate를 쓰려면 **도메인 작업부터 먼저 보정해야** 한다.
5. **thinking 재판단(cascade)은 계산·추론 문제에만 효과가 있었다**. 사실 판단 10문항에서 7/10이 10/10이 됐다.
   도메인 지식이 필요한 문제(BGL)에서는 효과가 작았다(+0.025). 모델이 모르는 규칙은 생각을 더 해도 알 수 없다.
6. **일반 생성은 확신도 정보가 없고**(AUROC 0.50), 형식 실패도 있었다(AG News 파싱 실패 13/120).

## 1. 조사한 개선 기법

| 기법 | 원리 | 라벨 필요 | 추가 비용 | 출처 |
|---|---|---|---|---|
| **few-shot** | 라벨이 붙은 예시를 프롬프트에 넣어 판단 기준을 알려준다 | 예시 몇 개 | 입력 토큰 증가 | 표준 ICL |
| **contextual calibration (cc)** | 내용 없는 입력("N/A")에 대한 답 분포를 모델의 사전 편향으로 보고 나눈다 | 없음 | 태스크당 3회 | Zhao et al. 2021 "Calibrate Before Use" |
| **batch calibration (bc)** | 판정할 배치 전체의 평균 확률을 사전 편향으로 보고 나눈다 | 없음 | 0 | Zhou et al. 2023 "Batch Calibration" |
| **permutation (perm)** | 선택지 순서를 바꿔 여러 번 묻고 평균낸다. 위치·라벨(A/B) 편향을 줄인다 | 없음 | 호출 × 선택지 수 | Zheng et al. 2023 (PriDe 계열) |
| **devcal** | dev 라벨로 temperature와 클래스별 bias를 학습한다(NLL 최소화) | dev 수십 건 | 0 | temperature scaling / Platt |
| **cascade** | 확신도가 낮은 건만 thinking으로 생각한 뒤 1토큰 판단으로 다시 판정한다 | 없음 | 해당 건만 수십 초 | 본 프로젝트 (System 1 → 2 에스컬레이션) |
| 조합 | fewshot+bc, fewshot+devcal, perm+cc | | | |

실험하지 않은 후보도 있다(8장): 선택지 설명 개선(판단 기준 명시), 질문 문장 여러 개로 앙상블, 코드로 계산한 특징을 state에 넣기, 큰 모델.

## 2. 벤치마크 설계

### 2.1 원칙
- **가짜 데이터가 아니라 공개된 실제 라벨 데이터**를 쓴다. 사내에서는 여기에 엔지니어가 라벨을 붙인 실제 로그를 더한다(커밋 금지).
- **dev/test를 분리한다.** few-shot 예시와 보정 파라미터는 dev에서만 고르고, 성능은 test에서만 잰다(누수 방지). 시드는 고정한다.
- **정확도만 보지 않는다.** 이 방식의 가치는 확신도에 있으므로 보정 지표와 선택적 예측 지표를 함께 본다.
- **비용을 같이 기록한다**(호출 수, 지연). 비용이 늘어나는 기법은 그만큼 이득이 있어야 채택한다.
- **신뢰구간(bootstrap 95%)을 같이 낸다.** 표본이 작아서 구간이 겹치면 "차이 없음"으로 본다.

### 2.2 태스크 (`bench/datasets.py`)
| 태스크 | 데이터 | 형식 | 크기 (dev/test) | 무엇을 보나 |
|---|---|---|---|---|
| **bgl** | Loghub BGL 2k: Blue Gene/L 슈퍼컴퓨터 실제 로그, 관리자 알림 라벨 | noul | 20 / 80 | **도메인 로그 판단**. 알림 50건, 정상 50건. 정상 중 절반은 **FATAL 수준인데 정상인 줄**(함정). 알림은 전부 FATAL이지만 FATAL 347줄 중 204줄이 정상이다. 완전히 같은 줄은 하나로 합쳤다 |
| **boolq** | BoolQ validation: 지문과 예/아니오 질문 | noul | 40 / 120 | 일반 독해, 예/아니오 치우침 |
| **agnews** | AG News test: 뉴스 4분류 | choice | 40 / 120 | 다중 선택, 위치 편향 |

데이터는 실행할 때 받아서 `bench/data/`에 캐시한다(gitignore). 라이선스 때문에 저장소에 넣지 않는다.
사내망에서 받을 수 없으면 집에서 받은 jsonl을 따로 옮긴다.

### 2.3 지표 (`bench/improve_eval.py`의 `metrics`)
| 지표 | 의미 | 좋은 방향 |
|---|---|---|
| acc (+95% CI) | 정확도 (1000회 bootstrap) | ↑ |
| macro-F1 | 클래스 불균형 보정 | ↑ |
| Brier | 확률 전체의 제곱오차 | ↓ |
| ECE | 확신도와 실제 정답률의 차이(10구간) | ↓ |
| **AUROC** | 확신도로 정답과 오답을 가르는 능력. 0.5면 무작위, **confidence gate에 핵심** | ↑ |
| **AURC** | 확신도 순으로 채택할 때의 위험-커버리지 곡선 면적 | ↓ |
| top50 | 확신도 상위 50%만 채택했을 때의 정확도 | ↑ |
| yes% | noul에서 "예"라고 답한 비율(정답 비율은 50%) | 0.5에 가까워야 |
| calls | 항목당 호출 수(비용) | ↓ |

### 2.4 기준선
- **plain**: 같은 모델, thinking 끔, JSON으로 답을 생성한다(`plain_decide`). 키가 어긋나면 관대하게 채점한다.
  파싱에 실패하면 균등 분포로 처리해 오답과 같은 효과를 준다.
- raw: 현재 운영 코드와 같은 프롬프트다.

## 3. 결과 (Qwen3.5-4B, 결과 원본: `bench/results_improve_qwen3.5-4b_local.json`)

### 3.1 BGL: 실제 로그 장애 판정 (n=80)

| cc | 0.662 | 0.56–0.78 | 0.598 | 0.268 | 0.391 | 0.353 | 0.84 | 1 |
| perm+cc | 0.675 | 0.57–0.78 | 0.541 | 0.212 | 0.428 | 0.326 | 0.75 | 2 |
| bc | 0.512 | 0.40–0.61 | 0.575 | 0.239 | 0.667 | 0.329 | 0.51 | 1 |
| fewshot | 0.537 | 0.42–0.65 | 0.706 | 0.389 | **0.944** | 0.168 | 0.99 | 1 |
| devcal | 0.475 | 0.38–0.57 | 0.559 | 0.254 | 0.764 | 0.284 | 0.40 | 1 |
| fewshot+bc | 0.775 | 0.69–0.86 | 0.306 | 0.080 | 0.806 | 0.089 | 0.75 | 1 |
| **fewshot+devcal** | **0.925** | **0.86–0.97** | **0.152** | **0.074** | 0.811 | **0.022** | 0.57 | 1 |

| cascade | 0.700 | 0.60–0.80 | 0.506 | 0.198 | 0.501 | 0.239 | 0.72 | 1.12 |

해석:
- raw는 "예"로 치우쳤고(75%), **오답에 더 확신했다**(AUROC 0.39). FATAL이라는 단어에 속았다.
- few-shot만 넣으면 거의 전부 "예"(99%)로 쏠려 정확도는 낮다. 그런데 AUROC 0.944로 **순서 정보는 거의 완벽하다**.
  예시가 판단 기준을 알려줬고, 기준선만 어긋난 상태다.
  → dev 라벨로 기준선을 맞추면(devcal) **0.925**가 된다. 라벨 없는 bc로 맞춰도 0.775다.
- perm, cc, bc 단독과 devcal 단독은 효과가 없거나 오히려 나빴다. **도메인 지식이 없는 상태에서 확률만 보정하면 소용이 없다.**
- cascade(28건 중 10건을 재판단, 768토큰 예산)는 +0.025에 그쳤다. **모델이 모르는 BGL의 알림 규칙은 생각을 더 해도 알 수 없다.**

### 3.4 사고 예산 실험 (별도, 사실 판단 10문항: 산술, 날짜, 글자 세기, 함정)

|---|---|---|---|
| thinking 끔 | 7/10 | 0.75 | 0.1초 |
| 256토큰에서 생각 중단 후 판단 | 8/10 | 0.81 | 12.6초 |
| 1024토큰까지 생각 후 판단 | **10/10** | 0.98 | 29.3초 |
- **여러 단계 계산이 필요한 문제에는 thinking이 결정적**이었다. 다만 생각을 **끝까지 마쳐야** 효과가 있었다.
- 생각을 마친 뒤의 확률은 0이나 1로 쏠려서 애매함 정보가 사라진다. 선행 연구의 보고와 같다.

### 3.5 비용 포함 결과 (항목당 평균, 가짜 서버 기준)
> 지연 시간은 서버에 따라 크게 달라진다(가짜 서버는 최적화 커널이 없어서 생성이 특히 느리다).
> **토큰 수는 서버가 바뀌어도 거의 그대로**라서 비용 비교의 기준으로는 토큰이 더 믿을 만하다.
> 원본: `bench/results_improve_cost_qwen3.5-4b_local.json`
> (`--plain --cascade 10 --cascade-budget 1024 --plain-thinking 5`)

| 태스크 | 방식 | 정확도 | 입력 토큰 | 출력 토큰 | 지연 p50 | 시간 (raw 대비) |
|---|---|---|---|---|---|---|
| **BGL** | raw | 0.675 | 112 | 1 | 107ms | 1× |
| | **fewshot+devcal** | **0.925** | 284 | **1** | 121ms | **1.1×** |
| | plain | 0.750 | 153 | 17 | 878ms | 8× |
| | cascade (28건 중 10건 thinking) | 0.700 | 263 | 124 | 107ms (p95 53초) | 57× |
| **BoolQ** | raw | 0.850 | 186 | 1 | 87ms | 1× |
| | fewshot | 0.800 | 1,083 | 1 | 305ms | 3.8× |
| | plain | 0.892 | 227 | 29 | 1,579ms | 18× |
| **AG News** | raw | 0.883 | 125 | 1 | 86ms | 1× |
| | bc | 0.900 | 125 | 1 | 86ms | 1× |
| | perm | 0.883 | 499 | 4 | 334ms | 3.9× |
| | plain | 0.875 | 166 | 21 | 931ms | 13× |

**plain+thinking(평소 방식) 표본: 태스크당 5건, 모두 15건**
| | 결과 | 출력 토큰 | 시간 |
|---|---|---|---|
| plain+thinking | 15건 중 **8건이 4096토큰 안에 생각을 끝내지 못해 답이 없었다**. 답을 낸 7건은 모두 정답 | 평균 약 3,300 | 건당 약 3분 |
| 같은 BGL 5건의 fewshot+devcal | 5/5 정답 | 1 | 132ms |

해석:
- **시간을 잡아먹는 건 출력 토큰이다.** 입력은 한 번에 병렬로 처리되고, 출력은 한 토큰씩 순서대로 생성되기 때문이다.
  few-shot은 입력을 2.5배 늘렸지만 시간은 1.1배로 거의 그대로였다. 반면 plain은 출력이 17~29토큰일 뿐인데 8~18배 느렸다.
- Jev 방식은 **항상 출력 1토큰**이다. 그래서 입력을 조금 늘리는 기법(few-shot)은 싸고, 호출 수를 늘리는 기법(perm)은 비싸다.
- **thinking은 출력 수천 토큰**이라 raw보다 1000배 이상 느리다. 게다가 예산(4096)이 모자라면 답이 아예 나오지 않는다. 운영에서는 예산 초과 처리가 필수다.
- 로그 판정에서 **fewshot+devcal은 raw와 거의 같은 비용(시간 1.1배)으로 가장 높은 정확도**를 냈다. plain보다 7배 빠르면서 17%p 높았다.

### 3.6 이전 결과와의 관계
- 쉬운 합성 60건: jev 60/60. 어려운 workflow 72건(다른 세션): jev 78%, plain 86%.
  확신도 0.8 이상만 채택하면 **92%**(39건).
- 종합하면 **"무엇을 모르는가"에 따라 처방이 다르다**.
  - 도메인 규칙을 모른다 → **few-shot + 보정**
  - 계산·추론이 필요하다 → **thinking cascade** 또는 **코드로 계산**
  - 일반 상식이나 분류 → **raw로 충분**

## 4. 권장 운영 전략 (실험 기반)

| 판단 유형 | 권장 구성 | 근거 |
|---|---|---|
| **도메인 로그/장애 판정** (모뎀 로그 포함) | 클래스별 대표 예시 2개 이상을 넣는 **few-shot** + 라벨 20~50건으로 **devcal**. 라벨이 없으면 **bc** | BGL 0.675 → 0.925 |
| 일반 분류, 라우팅 | **raw**. 배치 판정이면 **bc**를 추가(무료) | AG News, BoolQ |
| 계산, 날짜, 개수 판단 | **코드로 계산해서 state에 넣는다**. 불가피하면 thinking cascade | 사고 예산 실험 |
| 애매한 건 처리 | 보정된 확신도로 gate를 둔다: 높으면 자동 처리, 낮으면 cascade 또는 상위 모델 | AURC 개선 |
| 쓰지 말 것 | perm(비용 대비 효과 없음), cc(불안정), dev가 작을 때 devcal 단독 | 3장 |

## 5. 코드 반영 제안 (아직 운영 코드에는 없음)
1. **질문 스펙에 `examples` 추가**: `{"type": "noul", "instructions": ..., "examples": [{"state": ..., "answer": "yes"}, ...]}`
   → `build_user_content`가 예시 블록을 넣는다. MCP 스키마에도 추가한다.
2. **질문 스펙에 `calibration` 추가**: `{"temperature": T, "bias": [...]}` → `restricted_softmax` 앞에 적용한다.
   보정값은 `improve_eval.py`의 `fit_devcal`로 구한다. 반복해서 쓰는 질문은 파일로 저장해서 불러온다.
3. **`jev_decide_batch`에 `batch_calibrate: true` 옵션 추가**: 배치 평균을 사전 분포로 보고 나눈다. 비용 0.
   단, 배치의 클래스 분포가 한쪽으로 크게 치우치면 오히려 해롭다(주의 문구 필요).
4. **`escalate_below` + `think_budget`**: 확신도가 낮은 질문만 think-then-decide로 재판단한다.
   생각을 **끝까지 마칠 수 있는 예산**을 줘야 한다(1024 이상).

## 6. 한계
- 표본이 작다(80~120). BGL을 빼면 기법 간 차이가 대부분 신뢰구간 안이다.
- few-shot 예시는 시드 하나로 한 번만 뽑았다. **예시 선택에 따른 분산을 재지 않았다**(여러 시드로 반복 필요).
- dev가 작아서(20~40) devcal이 과적합할 수 있다(BoolQ ECE 악화).
- BGL 라벨은 관리자 규칙 기반이라, "알림"의 정의가 운영 조직마다 다르다. 이 점이 few-shot이 필수인 이유이기도 하다.
- cascade는 가짜 서버가 느려서 768토큰 예산과 태스크당 10건으로 제한했다. 대부분 예산에서 잘렸다. vLLM에서 예산을 늘려 다시 재야 한다.
- 4B 모델 하나로만 측정했다.

## 7. 재현 방법
```bash
uv sync --group bench                       # 집 PC: pandas, pyarrow (데이터 로드용)
python bench/improve_eval.py --tasks bgl    # 빠른 확인 (약 1분)
python bench/improve_eval.py --plain --cascade 10   # 전체 (가짜 서버 기준 약 40분)
python bench/improve_eval.py --plain --cascade 10 --cascade-budget 1024 --plain-thinking 5   # 비용 비교 포함 (약 1.5시간)
```
- 호출 결과는 `bench/out/cache.jsonl`에 캐시되어, 재실행하면 새 호출만 한다. 모델이 바뀌면 키도 바뀐다.
- 사내: `JEV_*` 환경변수만 바꿔서 그대로 실행한다. pandas가 없으면 집에서 만든 `bench/data/*.jsonl`을 옮겨두면 된다(로더가 캐시 파일을 먼저 쓴다).

## 8. 다음 실험 후보
1. **사내 실제 모뎀 로그로 BGL과 같은 설계를 한다**. 엔지니어 라벨 100~200건을 dev/test로 나누고 few-shot+devcal을 검증한다. **가장 중요하다.**
2. few-shot 예시 수(1/2/4/8)와 선택 방식(무작위, 어려운 예시, 대표 예시)을 비교하고 여러 시드로 분산을 잰다.
3. 선택지 설명에 판단 기준을 명시하는 효과를 본다(프롬프트 개선 vs few-shot).
4. 질문 문장 여러 개로 앙상블한다(perm보다 싼 대안).
5. cascade 예산을 1024~2048로 늘리고, gate 기준값별 정확도와 비용 곡선을 그린다.
6. Qwen3.8에서 같은 표를 다시 만든다(모델 크기에 따른 변화).
